When upserts don’t update but still write: Debugging Postgres performance at scale ↗

Datadog investigated a severe performance regression in their PostgreSQL metadata store where rolling out a high-throughput upsert query caused disk writes to double and WAL syncs to quadruple, despite most operations being no-ops. Using the pg_walinspect extension, they discovered that standard ON CONFLICT DO UPDATE statements unconditionally lock conflicting rows and assign transaction IDs, generating unnecessary WAL records and disk flushes even when row data does not change. To eliminate this hidden cost, they rewrote the logic using a data-modifying Common Table Expression with ON CONFLICT DO NOTHING to conditionally apply updates without locking existing rows. This approach successfully removed the unexpected WAL overhead while maintaining a single-query execution pattern and satisfying their data freshness requirements.
