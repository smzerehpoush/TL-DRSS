Should you use a log or a metric? ↗

Deciding whether to instrument application events with logs or metrics often causes confusion when building telemetry into software services. Logs are best used as insurance for reconstructive debugging, capturing detailed context at specific decision points to troubleshoot individual user issues or failures. In contrast, metrics suit pre-planned, continuous trend tracking over time—such as counters for signup funnels, gauges for queue depth, and distributions for cross-request durations. Standardizing shared attributes across telemetry types and filtering events at the SDK level enables seamless navigation between metrics, logs, and trace contexts.

SBD: We Have a Filesystem at Home ↗

To provide persistent state across host migrations for its Sprites environment, Fly.io initially used a customized JuiceFS setup backed by object storage and local SQLite metadata databases. However, asynchronous updates between separate metadata ledgers and object chunks caused disk corruption and broken checkpoints during ungraceful terminations. To eliminate this complexity, Fly.io replaced the system with the Sprites Block Device (SBD), an NBD daemon that exposes object storage directly to the kernel as an ext4-formatted block device. By storing volume metadata alongside data blocks in the object store, SBD guarantees a single source of truth, enabling deterministic volume snapshotting and significantly higher reliability under stress testing.

GitHub migrated its Git repository storage to Azure, but cross-region latency degraded write throughput for its busiest repositories due to repository-wide locking during quorum updates.
