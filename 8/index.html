Building multi-Region resiliency for AWS CloudFormation custom resource deployment ↗

AWS CloudFormation custom resources lack native multi-Region support, posing challenges for resilient deployments such as duplicate execution, lack of distributed locking, and no automated failover. This article presents an active-active multi-Region architecture to address these issues. The solution leverages cross-Region SNS fan-out to SQS queues in primary and secondary regions, with DynamoDB Global Tables providing distributed locking and idempotency to prevent duplicate processing. Automated failover is managed by Amazon Application Recovery Controller (ARC). This design ensures high availability, correctness, and automation for mission-critical custom resource operations across AWS Regions.

Session revocations at scale ↗

Canva addressed a critical performance bottleneck during deployments where hundreds of thousands of gateway instances simultaneously overloaded their MySQL database by loading large in-memory session revocation caches. They engineered a new system that leverages S3 as an intermediary cache. Asynchronous worker processes continuously partition revocation records into compact, sorted 30-minute binary chunks and upload them to S3 using optimistic concurrency control. Gateway pods now efficiently download these chunks directly from S3 on startup and for continuous updates, eliminating the database stampede. This solution dramatically improved deployment speeds, reduced MySQL read replicas, and decreased the in-memory cache footprint by 87.5%.

Unbiased Java CPU profiling with JFR in JDK 25 ↗

Traditional Java Flight Recorder (JFR) sampling can produce biased or incomplete results for CPU-bound workloads, forcing profilers to rely on unsupported internal JVM APIs like AsyncGetCallTrace for accurate CPU-time profiling. To eliminate this tradeoff between safety and accuracy, Datadog collaborated with SAP, Amazon, and Oracle in the OpenJDK community to introduce a first-class CPU profiling event in JDK 25. The new mechanism uses cooperative stack walking, which records lightweight execution points when CPU timers fire and defers stack unwinding to guaranteed safe states. This approach delivers accurate, production-safe CPU-time profiles directly within JFR without relying on fragile JVM internals.
