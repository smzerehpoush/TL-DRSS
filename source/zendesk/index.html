What happens when code becomes abundant ↗

This post examines how generative AI transforms software engineering by making code generation cheap and abundant, shifting the primary bottleneck from writing code to absorbing it. Drawing parallels to Liebig's law of the minimum in agriculture and the Toyota Production System in manufacturing, the author argues that unchecked code output merely creates unmanageable inventory rather than true throughput. To prevent architectural degradation, engineering teams must invest in crisp problem framing, lower the cost of verification through fast feedback loops, and enforce strong architectural conventions as guardrails. Ultimately, organizations should measure real system throughput and flow—such as lead times and change failure rates—rather than vanity metrics like lines of code or commit counts.

Heartbeats ↗

Zendesk uses application-generated synthetic traffic called heartbeats to ensure reliable monitoring and testing in low-traffic or quiet database clusters. By periodically injecting synthetic transactions into their MySQL-to-Kafka publishing pipeline and change streams, they eliminate false alarms caused by idle systems. This approach provides an always-on smoke test for data flows, verifies transactional consistency, and accurately calculates change stream lag during cross-region account migrations.

A Journey to Empowerment: How Zendesk Engineers Transformed Infrastructure Provisioning ↗

Zendesk tackled the fragmented and manual nature of self-service infrastructure provisioning by building a centralized platform called the Foundation Interface. Integrated into their Spinnaker deployment pipelines via webhooks, the system accepts service YAML configurations, validates parameters, converts them into Kubernetes Custom Resources, and orchestrates downstream operators. A built-in watchdog monitors provisioning statuses and reports back to Spinnaker to gate application deployments. This architecture eliminates provisioning inconsistencies, catches configuration errors early, and enables engineers to self-serve complex infrastructure components seamlessly.

Connecting Applications to Self-Service Datastores ↗

Zendesk eliminated manual, error-prone database credential management by building a zero-touch, self-service pipeline using Kubernetes. Instead of requiring developers to manually handle secrets via HashiCorp Vault, the system employs a mutating admission webhook that automatically injects an init container to fetch credentials and a sidecar container to manage token lifecycles. When credentials approach expiration, the sidecar safely evicts the pod, triggering a recreation cycle that seamlessly provides fresh credentials without requiring application code changes. This fully automated approach enhances security by keeping secrets entirely away from human operators and enforcing regular, automated rotation.

Resolving Incidents With The Remote Incident Console ↗

During production outages, engineers often need direct database access to assess issues and apply fixes, which presents significant security and credential-management challenges. Zendesk built the Remote Incident Console (RIC), a CLI-driven tool that spins up a targeted Kubernetes pod within the application namespace to provide secure, temporary access. The console uses proxy containers to abstract and hide real database credentials while routing connections through standard CLI tools like MySQL. Furthermore, the system integrates with Okta for access control and logs all commands to Splunk for complete auditability during and after incidents.

Less is More: Improving job execution by ditching the job executor ↗

Zendesk overhauled its long-running account move tooling by eliminating traditional distributed job executors, databases, and lock APIs in favor of a simpler, stateless streaming gRPC request model. By shifting job state persistence and retry logic to the client orchestrator, servers no longer need to manage complex distributed coordination. This architectural shift prevents dangling jobs, leverages standard load balancers for workload distribution, and drastically reduces the engineering effort required to integrate new datastores.

Simplifying Datastore Provisioning with Kubernetes Operators ↗

Zendesk replaced its manual, ticket-based datastore provisioning workflow with custom Kubernetes storage operators to eliminate weeks-long delays and human error. By defining datastore requirements in a simple application configuration file, engineering teams can automatically provision compliant cloud resources like Aurora, DynamoDB, and S3 during the deployment pipeline. The operators continuously monitor custom resources to enforce security baselines, handle network topology, and manage credentials without developer intervention. This self-service model successfully cuts provisioning times down to minutes while ensuring strict adherence to internal compliance standards.
