A Story of Delayed AWS Pipelines ↗

Booking.com investigated intermittent 15-minute delays in their Terraform CI/CD pipelines and discovered that the aws_organizations_organization data source unexpectedly triggered heavy, paginated API calls like ListAccounts and ListRoots. Because these rate limits apply organization-wide, concurrent executions across multiple teams exhausted the strict one-request-per-second quota and caused severe throttling via exponential backoff. To resolve this, Booking.com contributed a fix upstream to the Terraform AWS provider to make those extra API calls optional when only the organization ID is needed. This optimization eliminated nearly one million unnecessary weekly requests, recovered hundreds of pipeline-hours, and restored predictable pipeline execution speeds.

Breaking the Loop: How we migrated our backup catalog for 250+ MySQL clusters to AWS ↗

Booking.com migrated the backup catalog for over 250 production MySQL clusters from an on-premises self-managed database to Amazon RDS, eliminating a critical circular disaster recovery dependency where the backup system required the database it backed up to operate. The team combined this database migration with an operating system upgrade and a major version update of their backup orchestrator, Bacula, by deploying a parallel side-by-side stack. They utilized Infrastructure-as-Code via internal Terraform modules, over-provisioned the initial RDS instances to prioritize stability, and extended their internal control plane to route backups incrementally to the new cloud infrastructure. This phased rollout successfully modernized the backup pipeline while maintaining compliance, ensuring multi-region disaster recovery readiness without risking production availability.
